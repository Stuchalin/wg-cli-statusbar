# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

WGStatusBar is a macOS menu-bar app (AppKit hybrid, macOS 13+, swift-tools 5.9) that shows WireGuard interface status by parsing `wg show all dump` output and manages tunnels (`wg-quick up/down`) through the same daemon. The app runs as a regular user and reads status through the privileged root daemon `WGStatusBarHelper` over a unix socket; a direct process-runner fallback covers dev runs under `sudo` (status only — tunnel management requires the daemon).

## Commands

```bash
swift build                    # debug build (app + helper)
.build/debug/WGStatusBar       # run the app
swift build -c release         # release build
swift test                     # all tests
swift test --enable-code-coverage
swift test --filter HandshakeFreshnessTests/testFreshnessRecentHandshakeIsFresh   # single test
scripts/build-app.sh           # .app bundle: helper → Contents/MacOS, daemon scripts → Contents/Resources
sudo scripts/install-daemon.sh --binary .build/debug/WGStatusBarHelper   # manual daemon install (dev)
```

Live status requires the WireGuard CLI on the machine (`brew install wireguard-tools`). With the daemon installed no sudo is needed; without it the dev fallback is `sudo .build/debug/WGStatusBar` (process runner, picked automatically when the socket file is absent). Without `wg` the app still builds and runs, but the card shows the wg-missing state with install commands.

On the dev machine `xcode-select` points at CommandLineTools, which has no XCTest — run tests as `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test`.

## Architecture

Three targets (see `Package.swift`); note directory names don't match target names:

- `WGStatusBar` — executable target located at `Sources/App/main.swift`: no `@main`; `NSApplication` + `AppDelegate` + `setActivationPolicy(.accessory)` + `app.run()`. The delegate owns the model, the `StatusItemController`, and the `InstallerService` (callbacks wired there: success → immediate `refresh()` + `loadTunnels()` — the "after successful Install/Update" trigger physically lives here, not in the model; failure → one-tick error). Thin shell, no business logic.
- `WGStatusBarHelper` — executable target located at `Sources/Helper/main.swift`: thin shell over `DaemonServer` on `/var/run/wgstatusbar.sock`; setup errors print to stderr and exit non-zero (launchd `KeepAlive` restarts it). No unit tests (thin-main convention).
- `WGStatusBarCore` — library target split across `Sources/WGStatusBarCore/`, shared by both executables (the version constants compile into both so they cannot drift):
    - `WireGuardStatusBarCore.swift` — `WireGuardStatusModel` (ObservableObject), the process runner (`ProcessWGShowRunner`, injectable via `WGShowCommandRunning`; command and timeout injectable for runner tests), and `L10n`.
    - `HelperProtocol.swift` — wire protocol: `helperProtocolVersion` / `helperBuildNumber` constants, `encode(_:)`/`decode(response:)` for `show`/`list`/`up(String)`/`down(String)` requests and `ok`/`err` replies (codes `wgMissing`/`wgFailed`/`quickMissing` (wire `wg-quick-missing`)/`tunnelNotFound` (wire `tunnel-not-found`); `ok` payload is the show dump, the newline-separated `list` names, or empty for `up`/`down` — one set of payload rules covers all three).
    - `ChildProcessRunner.swift` — internal shared child-process runner used by both daemon executors: `runChildProcess(handle:executableURL:arguments:environment:timeout:killGrace:)` (TERM → SIGKILL after a grace → bounded wait that gives up even on an unkillable child; parallel pipe drain; `ChildProcessHandle` for task cancellation, moved here from `WGShowExecutor`), raw `ChildProcessResult { stdout, stderr, terminationStatus, timedOut }` — no error classification, callers (`WGShowExecutor`/`WGQuickExecutor`) translate into their own error types; `ChildProcessError { launchFailed, abandoned, cancelled }`. `environment: nil` inherits the daemon's environment, a non-empty dictionary replaces it entirely (the wg-quick PATH injection relies on that).
    - `DumpSanitizer.swift` — `sanitizeWGDump(String) -> String`: private key (interface line, field 2) and preshared key (peer line, field 3) → `(none)`; peer lines only after an interface line (same tracking as the parser). Fail-closed: an unrecognized line of 5+ fields (garbage or `wg` format drift after a wireguard-tools upgrade — daemon and wg versions are independent) leaves with both secret slots scrubbed, so secrets never reach the app even when the dump format changes.
    - `WGBinaryResolver.swift` — finds `wg` in `/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin` (MacPorts), `/usr/bin` (launchd has no user PATH); caches only successful resolves and revalidates the cached path each call, so both a later `brew install` and a `brew uninstall` are picked up without a daemon restart.
    - `WGShowExecutor.swift` — daemon-side runner: literal args `show all dump`, delegates to `runChildProcess` (behavior unchanged since the extraction); hard timeout (~3 s SIGTERM → SIGKILL after a grace → bounded wait that gives up even on an unkillable child so the sequential accept loop is never wedged); the whole reply budget (`timeout + 2 × killGrace` = 4 s) must stay under the client's 5 s deadline so the daemon always answers `err` before the client times out (defaults as `defaultTimeout`/`defaultKillGrace` constants, invariant pinned by tests), `WGShowExecutorError` (`wgMissing`/`timedOut`/`wgFailed`); returns raw output — sanitizing is not its job.
    - `WGQuickResolver.swift` — finds `wg-quick` in `/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin` (MacPorts), `/usr/bin` (`wgQuickBinarySearchPaths`, same order as `wg`); the same cache-with-revalidation contract as `WGBinaryResolver`; `searchDirectories` feeds the child PATH.
    - `WGQuickExecutor.swift` — daemon-side tunnel executor (`WGQuickExecuting { runUp/runDown }`, literal args `["up"|"down", name]`, arguments are not injectable — they are literal in production): resolves `wg-quick` (miss → `quickMissing`, no process launched), replaces the child's environment with `["PATH": …]` = resolver directories first + system tail, deduped (`/opt/homebrew/bin:/usr/local/bin:/opt/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` in production — under launchd the daemon has no Homebrew PATH, and `wg-quick` is `#!/usr/bin/env bash` needing bash ≥ 4 plus `wg`/`route`/`ifconfig` from PATH); `WGQuickExecutorError` (`quickMissing`/`timedOut`/`failed(String)` where the detail is the ~300-char stderr tail — daemon log only, never on the wire); `defaultOpTimeout = 8.0` / `defaultKillGrace = 0.5` → op budget 9 s.
    - `TunnelConfigStore.swift` — daemon-side config catalog: `tunnelConfigSearchPaths` (`/etc/wireguard`, `/usr/local/etc/wireguard`, `/opt/homebrew/etc/wireguard`, `/opt/local/etc/wireguard` — wg-quick's own CONFIG_SEARCH_PATHS plus the MacPorts prefix; missing directories are skipped); `names()` = `*.conf` basenames filtered by wg-quick's own interface-name regex `^[a-zA-Z0-9_=+.-]{1,15}$`, sorted, deduped, rescanned on every call (no cache — `list` arrives per menu open); `validate(_:)` = that shape check AND the name present in `names()` (both required: shape mirrors wg-quick one-to-one, presence kills guaranteed "No such file or directory" runs). Injectable FS (`TunnelConfigFileSystem`).
    - `HelperDaemon.swift` — `DaemonServer`: unlink+bind the socket (umask 0117 at bind so it never exists wider than 0660 root:admin, best-effort chown/chmod after), sequential accept-loop, one connection = one request, read deadline for silent clients, cancels wg (task cancellation → child kill) when the client disconnects mid-request, sanitizes the executor output before replying (the single point where secrets are stripped). Command routing: first word + argument — `show`/`list` (argument must be nil, a trailing word keeps it an unknown command) → executor/store; `up`/`down <name>` → `TunnelConfigStore.validate` → `WGQuickExecutor` (`ok` with no payload). Tunnel ops are NOT wrapped in the EOF-cancellation path used by `show` (SIGTERM mid-`up` would leave a half-applied tunnel — addresses, routes, DNS); they are bounded by the executor's op timeout and cancelled only by server shutdown. `init` takes injected `configStore`/`tunnelExecutor` with production defaults (helper `main.swift` unchanged).
    - `HelperClient.swift` — app-side transport shared by both clients: non-blocking connect + send + read-to-EOF under one deadline for the whole exchange, `SO_NOSIGPIPE`, poll loops with EINTR retries (`HelperClientError { connectionRefused, timedOut, badChannel }`); `decodeAndVerifyVersions(_:)` is the common reply part (decode + header version check — wrong protocol or older build → `daemonOutdated` even on `err`), command-specific `err`-code mapping stays in the clients.
    - `SocketWGShowRunner.swift` — app-side `show` client (`WGShowCommandRunning`; delegates the exchange to `HelperClient`, contract and `defaultTimeout = 5.0` unchanged) + `StatusFailure` (typed error: `wgMissing`, `commandTimeout`, `daemonOutdated`, `connectionRefused`, `badResponse`, `generic(String)`); tunnel-op codes cannot arrive for `show` and map defensively.
    - `SocketTunnelClient.swift` — app-side tunnel client, `TunnelCommandRunning { list() -> [String], up/down }` (injected into the model; production impl): `opTimeout = 16.0` covering the worst case of the daemon's sequential queue — a `show` tick started before the click (tick suppression only guards later ones) holds the daemon up to 4 s, then the op budget adds 9 s → 13 s < 16 s (invariant test takes the numbers from the constants); `err` codes → localized `.generic` (`error.wgquick_missing` / `error.tunnel_not_found` / `error.tunnel_op_failed`) — no new `StatusFailure` cases (the exhaustive switch in `ServiceState.derive` and its tests stay intact); detail from the wire is ignored (the daemon sends none); silence until the deadline → `.generic(error.tunnel_op_failed)`, not `.commandTimeout` (that text is about `wg show`).
    - `ServiceState.swift` — `helperSocketPath` and `ServiceState` (`absent`/`broken`/`outdated`/`installed`), derived from facts each tick by `ServiceState.derive(socketFileExists:outcome:)`.
    - `InstallerService.swift` — daemon install/uninstall via osascript `do shell script ... with administrator privileges`; static pure functions (script resolve, bundled-binary preflight, argv build, exit-code interpretation) are the tested part; the prompted run is not automatable.
    - `Model.swift` — `WGInterface { name, displayName, peers }`, `WGPeer { publicKey, endpoint, allowedIps, latestHandshake: Date?, rxBytes, txBytes: UInt64 }`, `TunnelInfo { name, isUp }` (a wg-quick config from the daemon's `list`; `isUp` is not daemon data — the model derives it from the current snapshot via `isTunnelUp(named:)`, recomputed on every successful tick and every `list` reply).
    - `DumpParser.swift` — global `parseWGShowDump(String) -> [WGInterface]` (tab-separated; interface line = 5 fields, peer line = 9; epoch `0` = never; `(none)` → nil).
    - `HandshakeFreshness.swift` — freshness enum with thresholds (fresh ≤ 120 s, aging ≤ 600 s) and `RouteScope` (fullTunnel/splitTunnel/none from allowed ips).
    - `Formatters.swift` — `formatBytes` (binary KiB/MiB/GiB) and `formatAgo` ("N ago").
    - `WireGuardTunnelNamer.swift` — resolves `utun2` → wg-quick config name (`work-vpn`) from `/var/run/wireguard/*.name` validated by an adjacent `<utun>.sock` with consistent mtime (|Δ| < 2 s, mirroring `get_real_interface` from wg-quick's darwin.bash — the sock is per-interface, so a recreated sock exposes a lingering stale `.name` on a reused utun); lock-protected cache with per-lookup re-validation of the `.name`/`.sock` pair (a reused utun must not show a stale config name), injectable file system.
    - `StatusCardView.swift` — `StatusCardViewModel` (pure, tested) + thin SwiftUI `StatusCardView`.
    - `TunnelRowView.swift` — `TunnelRowViewModel` (pure, tested: `isBusy` = this tunnel's operation in flight, `isEnabled` = no operation in flight at all) + SwiftUI `TunnelRowView` (●/○ dot, `ProgressView` spinner when busy, hit-testing off and dimmed while disabled, VoiceOver label `tunnel.accessibility.on/off`; observes the model so spinner/clickability/isUp update live without a menu rebuild).
    - `StatusItemController.swift` — owns `NSStatusItem` and `NSMenu`; menu structure as data (`StatusMenuStructure`/`StatusMenuFactory`, tested; tunnel rows reach the factory via a `tunnelItemProvider` closure, same pattern as `cardItemProvider`) + `CardMenuItem`/`TunnelMenuItem` (native highlight disabled; clicks inside don't close the menu) + `StatusIcon` (menu-bar PDF icons, template) + legend visibility (`isLegendVisible` lives here so it survives `menuNeedsUpdate` rebuilds — the card's `@State` resets with each new `NSHostingView`; seeded into the card via `initialLegendVisible`, the ⓘ toggle reports back via `onLegendChange`, and the card re-measure is dispatched to the next run-loop pass — a synchronous `fittingSize` read would see the pre-render height and the ⓘ row would stay clipped until the next tick). `menuNeedsUpdate` also calls `model.loadTunnels()`; a separate `$tunnels` subscription rebuilds the section while the menu is open (the `list` reply is async — without it the section would appear only on the second open; a closed menu just rebuilds fresh next time).

Data flow: `WireGuardStatusModel.refresh()` picks the runner from facts on each tick — socket file exists (injectable `socketExists` probe) → `SocketWGShowRunner` over `/var/run/wgstatusbar.sock` (connect, send `show`, read to EOF under a 5 s deadline); no socket → the injected `commandRunner` (production: `ProcessWGShowRunner` = `/bin/zsh -lc "wg show all dump"`, login shell so Homebrew's `wg` is found on PATH; dev/sudo fallback). The dump arrives already sanitized from the daemon; it is parsed via `parseWGShowDump`, `displayName`s resolved through the namer (lazy rescan only for an unknown utun; `forceNameRescan: true` from the ⌘R menu item), then `@Published` state updated on the main actor. A `Timer` re-fires refresh every 5 seconds. `lastFailure: StatusFailure?` lives one refresh cycle (`lastError: String?` is computed from it for the card); `serviceState` is recomputed each tick. Data from the last successful tick stays visible under a 10 s grace (`stalenessLimit`; a failed tick sets only `lastFailure`, never clears `interfaces`); past the limit the snapshot is stale (`isDataStale`, computed from `lastSuccessAt` set by the last successful tick) — the card dims it (opacity 0.5 + `status.stale_data` marker) and it no longer feeds the icon (`showsConnected`).

The menu is rebuilt in `menuNeedsUpdate` (always fresh on open): first item is the SwiftUI card in an `NSHostingView` (`CardMenuItem`, highlight off), then native items Refresh ⌘R / Open Configs ⌘O, then the Tunnels section, then the service item (from `model.serviceState`: `absent` → Install, `broken`/`outdated` → Update, `installed` → Remove) / Quit ⌘Q. The Tunnels section (separator + disabled header + one row per tunnel) sits between Open Configs and the service item and exists only when `serviceState == .installed && !tunnels.isEmpty` — an old daemon answers `list` as unknown command → reported outdated → Update item, no section. Rows are SwiftUI `TunnelRowView`s in `NSHostingView`s (`TunnelMenuItem`); a click calls `model.toggleTunnel(named:)`. One operation at a time: while `inFlightTunnels` is non-empty every row is non-clickable and dimmed, and Refresh ⌘R is disabled too (a click would be a silently suppressed no-op — the tick is paused).

Tunnels data flow: `loadTunnels()` runs only when `serviceState == .installed` (an old daemon must not be poked) on three triggers — menu open (`menuNeedsUpdate`), after an up/down reply, and after a successful Install/Update (`installer.onSuccess` in `main.swift`) — never in the 5-second tick; client errors are swallowed silently (menu data is opportunistic, it must not fake a card error in the sudo dev fallback). `isUp` is derived, never fetched: a tunnel is up ⟺ some interface's `displayName` equals its name (`isTunnelUp(named:)`; honest limitation — when the namer fails to resolve, the row reads "down" and an up-click errs with a generic operation error, and the mismatch lives until the tunnel is recreated). `toggleTunnel(named:)` inserts the name into `inFlightTunnels` → sends up/down (direction from `isUp`) → removes the name; success → immediate `refresh()` + `loadTunnels()`; failure → one-tick `lastFailure` + `loadTunnels()` **without** `refresh()` (the refresh prologue erases `lastFailure` synchronously — the error would never render; the next 5-s tick converges the data). While `inFlightTunnels` is non-empty `refresh()` returns immediately (no error, no `serviceState` change — the queued-show-silence would read as `broken`) and `isDataStale` is forced false (the 13 s worst-case queue outlives the 10 s `stalenessLimit`; without this the icon would dim mid-operation).

Security constraint: the raw dump contains secrets (private key, preshared key) — never log it anywhere. The daemon strips secret fields via `sanitizeWGDump` before anything leaves it, so secrets never enter the app process; the parser additionally skips them.

Privileged daemon details:

- Wire protocol (line-based, one connection = one request): `→ show | list | up <name> | down <name>`; `← ok <protocol> <build>\n<dump-or-names-or-empty>`; `← err <protocol> <build> <code>[ <detail>]` with codes `wg-missing` | `wg-failed` | `wg-quick-missing` | `tunnel-not-found`. Both version numbers appear in every reply, including `err` — outdated detection works on error answers too (an old daemon answers `list`/`up` as unknown command → `err wg-failed` → still carries versions → outdated). Tunnel-op `err` replies carry **code only, no detail**: wg-quick's stderr echoes executed commands (including Pre/PostUp hooks from the config) and child-wg errors can quote config lines, so the stderr tail is written to the daemon's stderr (→ `/var/log/wgstatusbar-helper.log` via the plist) and never crosses the wire.
- Budget invariants (pinned by tests, numbers from the constants): `show` — `WGShowExecutor` 3.0 + 2 × 0.5 = 4.0 s under the show client's 5.0 s deadline; tunnel ops — `WGQuickExecutor` 8.0 + 2 × 0.5 = 9.0 s; worst-case sequential queue (a `show` started before the op) 4.0 + 9.0 = 13.0 s < `SocketTunnelClient.opTimeout` 16.0 s, so the daemon always answers before the client gives up.
- wg-quick PATH invariant: the executor replaces the child's whole environment with `PATH = /opt/homebrew/bin:/usr/local/bin:/opt/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` (resolver dirs first, system tail, deduped; pinned by a test). Under launchd the daemon has no Homebrew PATH — `wg-quick` is `#!/usr/bin/env bash` requiring bash ≥ 4 (system 3.2 dies with "Version mismatch") and calls `wg`/`route`/`ifconfig`/`networksetup` from PATH; verified empirically on the dev machine (launchd PATH → fails, brew-first PATH → works).
- Version constants live in `HelperProtocol.swift` (Core): `helperProtocolVersion` is compared for equality (bump only on breaking format changes); `helperBuildNumber` is monotonic — **bump it whenever helper code changes (release checklist)**; an app carrying a newer build reports the daemon `outdated` and shows the Update menu item.
- Service state is derived, never stored: no socket file → `absent`; socket present but connect refused / silence until the client deadline / garbage / instant EOF → `broken`; wrong protocol or older build → `outdated`; healthy → `installed`. `wgMissing`/`generic` errors don't affect service state (the daemon is fine, wg is the problem).
- Paths: socket `/var/run/wgstatusbar.sock` (0660 root:admin; the server unlinks a stale file before binding); helper binary `/Library/PrivilegedHelperTools/com.stuchalin.wgstatusbar.helper` (755 root:wheel); plist `/Library/LaunchDaemons/com.stuchalin.wgstatusbar.helper.plist` (`RunAtLoad` + `KeepAlive`, stderr → `/var/log/wgstatusbar-helper.log`).
- Install scripts: `scripts/install-daemon.sh --binary <path>` (idempotent: bootout ignoring "not loaded" → copy to a temp name + atomic rename over the live binary, so an async-bootout old daemon is not truncated under a running process → rm the socket file before bootstrap — the old daemon never rebinds, so only the new daemon's bind can recreate it and the wait below is a real "new daemon is up" signal on updates too, not just fresh installs → bootstrap system with a short retry → bounded wait until the daemon answers — a `show` request over `nc -U` gated on an `ok`/`err` reply header, not just socket-file existence: `bind()` creates the file before `listen()`, so a file-only check can pass in the bind→listen window and the app's immediate post-install refresh would hit a refused connect and mark the fresh service broken for a tick — so the refresh doesn't race into the fallback runner, a stale socket, the old daemon, or that refused connect) and `scripts/uninstall-daemon.sh` (bootout → rm plist, binary, socket, log); both ship in the .app's `Contents/Resources/` (`build-app.sh` also copies the helper binary to `Contents/MacOS/`).
- Install flow from the menu: `StatusItemController.performStatusAction` → `ServiceInstalling` (InstallerService) → osascript with the system password/Touch ID prompt. Cancelled prompt is a silent no-op; success triggers an immediate `refresh()`; script failure puts its stderr into the one-tick error.
- Accepted risk (documented in README): the install path runs a root shell script from the user-writable app bundle with no checksum (TOCTOU); the daemon likewise executes `wg` — and now `wg-quick` — from user-writable Homebrew paths as root (same local-user→root family). `wg-quick` additionally executes each config's Pre/PostUp (Pre/PostDown) hooks as root, and the configs live in user-writable directories — editing a config is arbitrary-code-as-root on toggle. There is deliberately no mutual exclusion between tunnels (wg-quick keeps several interfaces; two full-tunnels raised together fight over the default route and system DNS — README warns). The real fix is Developer ID + SMAppService plus a root-owned copy of `wg`/`wg-quick` (and configs) at install time, a future migration the protocol is designed for (transport change only).

Domain rules:

- Peer `isActive` = handshake freshness is `fresh` or `aging` (green ≤ 2 min, orange ≤ 10 min, inclusive).
- Interface `isConnected` = any of its peers is active.
- Menu-bar icon flips between `StatusIconOn`/`StatusIconOff` (vector PDFs in `Resources/`, loaded via `Bundle.module`, `isTemplate` so AppKit recolors for light/dark; error state shows Off). The icon and `menu.title.on/off` (the VoiceOver accessibility label) read `showsConnected` = `isAnyConnected && !isDataStale` — a snapshot older than `stalenessLimit` never lights the icon, so losing the source dims the shield within ~10–15 s (grace + one 5 s tick) instead of freezing it "on"; a single failed tick inside the grace causes no flicker. `isAnyConnected` stays the plain data-level truth.

## Localization

All UI strings go through `L10n.string(key, args...)` (loads from `.module` bundle). Every new key must be added to **both** `Sources/WGStatusBarCore/Resources/en.lproj/Localizable.strings` and `ru.lproj/Localizable.strings`; format placeholders use `%@` only (numbers passed as strings).

## Testing notes

- Tests use `@testable import WGStatusBarCore`. Injection points on the model: `WireGuardStatusModel(testing:)` injects interfaces directly (no timer/network), `init(commandRunner:tunnelNamer:)` injects protocol mocks for refresh-flow tests, `init(commandRunner:tunnelNamer:socketExists:socketPath:)` additionally injects the socket probe for service-state tests; the same full init takes `now: () -> Date` for staleness-grace tests (a frozen `FakeClock`) and `tunnelCommandRunner: TunnelCommandRunning` for tunnel tests (mock with counters and programmable results). Non-empty interfaces injected via `init(testing:)` always read as stale (`lastSuccessAt == nil`), so "on" assertions on `showsConnected`/`menuTitle` must go through a successful refresh (`makeRefreshedModel` in `WGStatusBarTests`).
- Parser tests call the global `parseWGShowDump(_:)` with fixture strings — no process spawning there. Tests spawning processes are `ProcessWGShowRunnerTests`, `WGShowExecutorTests` and `WGQuickExecutorTests`: short-lived executable stubs with injected small timeouts. `WGQuickExecutorTests` stubs are zsh scripts resolved through an injected single-candidate `searchPaths` (arguments are literal `["up"|"down", name]` and are asserted via marker files, not injected); the PATH test has a stub print `$PATH` and asserts the brew directories precede the system ones; timeout tests use ≥1.5 s deadlines — with a replaced environment (PATH only) a zsh script needs ~0.5 s to reach its first line, so a 0.3 s TERM would kill the stub before it sleeps.
- Daemon socket logic is tested in one process: `HelperDaemonTests` runs a real `DaemonServer` on a tmp socket with a stub executor (plus a stub config store / stub tunnel executor for the `list`/`up`/`down` routing, invalid-name, error-mapping and EOF-during-op cases); `SocketWGShowRunnerTests` and `SocketTunnelClientTests` drive the clients against it — no root, no real `wg` (a DaemonServer needs the stub dump to end with `\n`, like real `wg` output, or the client rejects it as truncated). `SocketTunnelClientTests` also pins the budget invariant (constants only).
- `InstallerServiceTests` cover the pure static functions only (script resolve, osascript argv, exit-code interpretation) — the privileged prompt is not automatable.
- Namer tests inject a fake file system; `TunnelConfigStoreTests` the same way (`TunnelConfigFileSystem`); `WGQuickResolverTests` mirror `WGBinaryResolverTests` with an injected `fileExists`. Card, menu and tunnel-row logic are tested through `StatusCardViewModel`, `StatusMenuStructure`, `TunnelRowViewModel`, `StatusItemController.performStatusAction` and `StatusItemController.iconConnected(for:)` (no `NSStatusItem`/`NSHostingView` in tests).
