# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

WGStatusBar is a macOS menu-bar app (AppKit hybrid, macOS 13+, swift-tools 5.9) that shows WireGuard interface status by parsing `wg show all dump` output and manages tunnels (`wg-quick up/down`) through the same daemon. The app runs as a regular user and reads status through the privileged root daemon `WGStatusBarHelper` over a unix socket; a direct process-runner fallback covers dev runs under `sudo` (status only — tunnel management requires the daemon).

## Commands

```bash
swift build                    # debug build (app + helper)
.build/debug/WGStatusBar       # run the app
swift build -c release         # release build
swift test                     # all tests
swift test --enable-code-coverage
swift test --filter HandshakeFreshnessTests/testFreshnessRecentHandshakeIsFresh   # single test
scripts/build-app.sh           # .app bundle: helper → Contents/MacOS, daemon scripts → Contents/Resources
sudo scripts/install-daemon.sh --binary .build/debug/WGStatusBarHelper   # manual daemon install (dev)
```

Live status requires the WireGuard CLI on the machine (`brew install wireguard-tools`). With the daemon installed no sudo is needed; without it the dev fallback is `sudo .build/debug/WGStatusBar` (process runner, picked automatically when the socket file is absent). Without `wg` the app still builds and runs, but the card shows the wg-missing state with install commands.

On the dev machine `xcode-select` points at CommandLineTools, which has no XCTest — run tests as `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer swift test`.

## Architecture

Three targets (see `Package.swift`); note directory names don't match target names:

- `WGStatusBar` — executable target located at `Sources/App/main.swift`: no `@main`; `NSApplication` + `AppDelegate` + `setActivationPolicy(.accessory)` + `app.run()`. The delegate owns the model, the `StatusItemController`, and the `InstallerService` (callbacks wired there: success → immediate `refresh()` only — no `loadTunnels()` here: refresh completes asynchronously, so its guard would still see the pre-install `serviceState` and reject the call as dead code; the tunnel state is pulled by the `serviceState` transition in `StatusItemController` (menu open) or the next menu open; failure → one-tick error). Thin shell, no business logic.
- `WGStatusBarHelper` — executable target located at `Sources/Helper/main.swift`: thin shell over `DaemonServer` on `/var/run/wgstatusbar.sock`; setup errors print to stderr and exit non-zero (launchd `KeepAlive` restarts it). No unit tests (thin-main convention).
- `WGStatusBarCore` — library target split across `Sources/WGStatusBarCore/`, shared by both executables (the version constants compile into both so they cannot drift):
    - `WireGuardStatusBarCore.swift` — `WireGuardStatusModel` (ObservableObject), the process runner (`ProcessWGShowRunner`, injectable via `WGShowCommandRunning`; command and timeout injectable for runner tests), and `L10n`.
    - `HelperProtocol.swift` — wire protocol: `helperProtocolVersion` / `helperBuildNumber` constants, `encode(_:)`/`decode(response:)` for `show`/`list`/`state`/`up(String)`/`down(String)` requests and `ok`/`err` replies (codes `wgMissing`/`wgFailed`/`quickMissing` (wire `wg-quick-missing`)/`tunnelNotFound` (wire `tunnel-not-found`); `ok` payload is the show dump, the newline-separated `list` names, the `state` lines — always three tab-separated fields, `name\tup\tutunN` for an up tunnel (non-empty utun) / `name\tdown\t` for a down one (empty third field), empty payload = no configs — or empty for `up`/`down`).
    - `ChildProcessRunner.swift` — internal shared child-process runner used by both daemon executors: an async `runChildProcess(executableURL:arguments:environment:timeout:killGrace:stderrKillMarker:markerKillDelay:)` that owns the `ChildProcessHandle` and the whole cancellation wiring (`withTaskCancellationHandler` + detached task off the cooperative pool; both executors call this one), delegating to the sync `runChildProcess(handle:…)` core (TERM → SIGKILL after a grace → bounded wait that gives up even on an unkillable child; parallel pipe drain — stderr incremental (accumulates for the error tail + optional marker watch); the explicit `handle:` param stays for the register→cancel→run race test), raw `ChildProcessResult { stdout, stderr, terminationStatus, terminationReason, timedOut, stderrMarkerSeen }` — no error classification, callers (`WGShowExecutor`/`WGQuickExecutor`) catch `ChildProcessError { launchFailed, abandoned, cancelled }` and translate into their own error types. `environment: nil` inherits the daemon's environment, a non-empty dictionary replaces it entirely (the wg-quick PATH injection relies on that). Two bounded-wait rules keep the daemon's sequential accept-loop alive no matter what: the `abandoned` wait-after-SIGKILL, and the post-exit pipe-EOF wait — EOF can be withheld forever by a surviving grandchild (the daemonized `wireguard-go` inherits wg-quick's stdout/stderr), so drains are bounded by the same `timeout + 2 × killGrace` budget and turn into `abandoned` instead of hanging — a child exiting exactly at the budget boundary with already-closed pipes is still classified from its data: the zero-remaining-budget `wait` checks the drain group once, instantly, instead of throwing blind. The optional `stderrKillMarker` is for children that never exit on success (wg-quick's launchd `wait`, see the executor below): when the marker appears on stderr as a complete line (`stderrContainsLine` — occurrences inside other lines don't count: wg-quick echoes every hook as `[#] <command>` before running it, and PreUp hooks run before set_config, so a hook whose text or output carries the marker substring must not fake the completion signal — an early kill there would answer ok for a half-configured tunnel; a hook deliberately printing the exact marker line is indistinguishable, subsumed by the accepted configs-are-code risk) the runner SIGKILLs the child after `markerKillDelay` (KILL, not TERM — TERM would run the still-installed teardown traps; the delay lets the script finish spawning its monitor subshell) and returns `stderrMarkerSeen: true` without waiting for pipe EOF (buffers unread — the drain tasks end later, when the pipe holders die, bounded by live tunnels); the one marker outcome where the caller reads stderr — self-exited nonzero without the timeout latch (the failed-PostUp case) — gets the accumulated stderr as a stateQueue-protected snapshot after a short bounded grace (0.5 s, clamped to the remaining budget) that lets the drain task read what the dead child already wrote into the pipe, never waiting for EOF; task cancellation wins even here (shutdown → `cancelled`, not a phantom marker-ok), and a child that exited on its own before the kill is returned with its own status+`terminationReason` — marker-vs-failure classification is the caller's, like every other branch.
    - `DumpSanitizer.swift` — `sanitizeWGDump(String) -> String`: private key (interface line, field 2) and preshared key (peer line, field 3) → `(none)`; peer lines only after an interface line (same tracking as the parser). Fail-closed: an unrecognized line of 5+ fields (garbage or `wg` format drift after a wireguard-tools upgrade — daemon and wg versions are independent) leaves with both secret slots scrubbed, so secrets never reach the app even when the dump format changes.
    - `WGBinaryResolver.swift` — finds `wg` in `/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin` (MacPorts), `/usr/bin` (launchd has no user PATH); caches only successful resolves and revalidates the cached path each call, so both a later `brew install` and a `brew uninstall` are picked up without a daemon restart.
    - `WGShowExecutor.swift` — daemon-side runner: literal args `show all dump`, delegates to `runChildProcess` (behavior unchanged since the extraction); hard timeout (~3 s SIGTERM → SIGKILL after a grace → bounded wait that gives up even on an unkillable child so the sequential accept loop is never wedged); the whole reply budget (`timeout + 2 × killGrace` = 4 s) must stay under the client's 5 s deadline so the daemon always answers `err` before the client times out (defaults as `defaultTimeout`/`defaultKillGrace` constants, invariant pinned by tests), `WGShowExecutorError` (`wgMissing`/`timedOut`/`wgFailed`); returns raw output — sanitizing is not its job.
    - `WGQuickResolver.swift` — finds `wg-quick` in `/opt/homebrew/bin`, `/usr/local/bin`, `/opt/local/bin` (MacPorts), `/usr/bin` (`wgQuickBinarySearchPaths`, same order as `wg`); the same cache-with-revalidation contract as `WGBinaryResolver`; `searchDirectories` feeds the child PATH.
    - `WGQuickExecutor.swift` — daemon-side tunnel executor (`WGQuickExecuting { runUp/runDown }`, literal args `["up"|"down", name]`, arguments are not injectable — they are literal in production): resolves `wg-quick` (miss → `quickMissing`, no process launched), replaces the child's environment with `["PATH": …]` = resolver directories first + system tail, deduped (`/opt/homebrew/bin:/usr/local/bin:/opt/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` in production — under launchd the daemon has no Homebrew PATH, and `wg-quick` is `#!/usr/bin/env bash` needing bash ≥ 4 plus `wg`/`route`/`ifconfig` from PATH); `WGQuickExecutorError` (`quickMissing`/`timedOut`/`failed(String)` where the detail is the ~300-char stderr tail — daemon log only, never on the wire; in the marker branch the tail is snapshot-collected only for the self-exited-nonzero outcome, `exit status N` remains the empty-stderr fallback, and the killed-with-dead-probe outcome carries a textual `killed by signal N …` detail — stderr is unread in the kill branch); `defaultOpTimeout = 8.0` / `defaultKillGrace = 0.5` → op budget 9 s. A successful darwin `wg-quick up` does NOT exit by itself: running as root its `detect_launchd` sees a `domain =` line in `launchctl procinfo` (true for any root-spawned process, launchd parent or not — observed in the wild) and the script ends in `wait`, alive as long as the tunnel. Success is therefore detected, not awaited: runUp passes `upMonitorMarker` (`"[+] Backgrounding route monitor"` — the monitor-daemon announcement printed after addresses/routes/DNS, before the launchd `wait`; matched as a whole stderr line — hook echoes `[#] …` carrying the substring don't count, see ChildProcessRunner) with `upMonitorKillDelay = 1.0` (the delay's floor is the monitor subshell's birth, which the marker precedes; its real job is a grace window for the PostUp hooks — under the daemon wg-quick never exits by itself on success, so a self-exit after the marker is always a failure and the runner honors self-exits for exactly this window; a hook that outlives the window is SIGKILLed mid-flight together with the script: the reply is ok — the marker has proven the tunnel setup — while the orphaned hook's late failure is unobservable and wg-quick's teardown trap never runs (the CLI would abort, tear the tunnel down and exit nonzero); no finite reply budget covers unbounded hooks, and a longer window would slow every successful up and widen the TERM/KILL race, so the bound is deliberate; KILL then bypasses the still-installed teardown traps, the tunnel, route monitor and daemonized `wireguard-go` survive); `stderrMarkerSeen` → ok only when the script exited 0 by itself or was killed by the marker KILL **with the tunnel still alive** — the kill-ok is probe-confirmed (`tunnelIsUp`): between the marker and the KILL a failed PostUp's teardown trap may finish dismantling the tunnel, and an unconditional ok there would be a false success over a dead tunnel (a dead probe after the kill is an honest `failed`; a trap caught mid-flight still probes "up" — that residual ok self-heals on the next show tick); the marker is printed before the PostUp hooks with the teardown trap still installed (cmd_up: `monitor_daemon` → `execute_hooks POST_UP` → `trap -`), so a self-exited nonzero status after the marker is an honest `failed` (under wg-quick's `set -e` a failed PostUp aborts the script and the trap dismantles the tunnel; the daemon log carries the snapshot stderr tail — the only diagnostic channel, since the wire never does), and a marker-vs-TIMEOUT race (marker in the budget's last second) falls through to the probe. Fallback when a future wg-quick rewords the marker: the timedOut/abandoned paths probe `tunnelIsUp(name:)` — the `get_real_interface` pair one-to-one: non-empty `utun*` in `/var/run/wireguard/<name>.name`, `<utun>.sock` must be an actual socket (`-S`, not just an existing path) with the pair's mtimes within 2 s (same correlation the namer uses; injectable FS); honest limitation: the pair is born in `add_if` before set_config/addresses/routes/DNS, so the probe proves "the interface exists", not "setup completed" — that completion signal is the marker's alone, and a wrong probe verdict self-heals on the next 5-s show tick. Tunnel up → ok (slower: the full 9 s budget), else honest `timedOut`. `down` never hangs (`wait` exists only on the up path) — no marker, no probe.
    - `TunnelConfigStore.swift` — daemon-side config catalog: `tunnelConfigSearchPaths` (`/etc/wireguard`, `/usr/local/etc/wireguard`, `/opt/homebrew/etc/wireguard`, `/opt/local/etc/wireguard` — wg-quick's own CONFIG_SEARCH_PATHS plus the MacPorts prefix; missing directories are skipped; known mixed-install niche: a brew-resolved wg-quick does not search `/opt/local`, so a config living only there is listed and validated yet `wg-quick up` fails "does not exist" — an explicit op error, no state corruption); `names()` = `*.conf` basenames filtered by wg-quick's own interface-name regex `^[a-zA-Z0-9_=+.-]{1,15}$`, sorted, deduped, rescanned on every call (no cache — `state` arrives per menu open, and the legacy `list` from older apps does too); `validate(_:)` = that shape check AND the name present in `names()` (both required: shape mirrors wg-quick one-to-one, presence kills guaranteed "No such file or directory" runs). Injectable FS (`TunnelConfigFileSystem`).
    - `HelperDaemon.swift` — `DaemonServer`: unlink+bind the socket (umask 0117 at bind so it never exists wider than 0660 root:admin, best-effort chown/chmod after), sequential accept-loop, one connection = one request, read deadline for silent clients, cancels wg (task cancellation → child kill) when the client disconnects mid-request, sanitizes the executor output before replying (the single point where secrets are stripped). Command routing: first word + argument — `show`/`list`/`state` (argument must be nil, a trailing word keeps it an unknown command) → executor/store/reader; `state` = `configStore.names()` × `WireGuardRuntimeReader.readPairs()` — a fresh local scan on every request (no processes, no cache — a cached reader would quietly repeat the tunnel-state bug), a config is up ⟺ the reader holds a valid pair for its name, reply lines `name\tup\tutunN` / `name\tdown\t`; `up`/`down <name>` → `TunnelConfigStore.validate` → `WGQuickExecutor` (`ok` with no payload). Tunnel ops are NOT wrapped in the EOF-cancellation path used by `show` (SIGTERM mid-`up` would leave a half-applied tunnel — addresses, routes, DNS); they are bounded by the executor's op timeout and cancelled only by server shutdown. `init` takes injected `configStore`/`tunnelExecutor`/`runtimeReader` with production defaults (helper `main.swift` unchanged).
    - `HelperClient.swift` — app-side transport shared by both clients: non-blocking connect + send + read-to-EOF under one deadline for the whole exchange, `SO_NOSIGPIPE`, poll loops with EINTR retries (`HelperClientError { connectionRefused, timedOut, badChannel }`); `decodeAndVerifyVersions(_:)` is the common reply part (decode + header version check — wrong protocol or older build → `daemonOutdated` even on `err`), command-specific `err`-code mapping stays in the clients.
    - `SocketWGShowRunner.swift` — app-side `show` client (`WGShowCommandRunning`; delegates the exchange to `HelperClient`, contract and `defaultTimeout = 5.0` unchanged) + `StatusFailure` (typed error: `wgMissing`, `commandTimeout`, `daemonOutdated`, `connectionRefused`, `badResponse`, `generic(String)`); tunnel-op codes cannot arrive for `show` and map defensively.
    - `SocketTunnelClient.swift` — app-side tunnel client, `TunnelCommandRunning { state() -> [TunnelState], up/down }` (injected into the model; production impl): `state()` shares the transport, version check and err mapping with the ops and parses the three-field lines (split by `\t` with `omittingEmptySubsequences: false` — a default split eats the empty third field of down lines; exactly 3 fields and a non-empty name, `up` requires a non-empty utun, `down` an empty one; the line split also keeps empty subsequences with only the payload's single trailing `\n` terminator dropped — a blank line between records and a lone `\n` payload are off-format → `badResponse`, not a silently skipped line or "no configs"); the client-side `list()` is gone (dead code once the model switched to `state`) while the daemon keeps serving the wire `list` for older apps; `opTimeout = 16.0` covering the worst case of the daemon's sequential queue — a `show` tick started before the click (tick suppression only guards later ones) holds the daemon up to 4 s, then the op budget adds 9 s → 13 s < 16 s, exactly **one** op per queue (the model-level one-op guard, below, keeps it at one; a second op would need 22 s) — invariant test takes the numbers from the constants; `err` codes → localized `.generic` (`error.wgquick_missing` / `error.tunnel_not_found` / `error.tunnel_op_failed`) — no new `StatusFailure` cases (the exhaustive switch in `ServiceState.derive` and its tests stay intact), except the defensive `wg-missing` branch which maps to the typed `StatusFailure.wgMissing` (a healthy daemon never sends it for tunnel ops — a missing `wg` inside wg-quick surfaces as `wg-failed`); detail from the wire is ignored (the daemon sends none, and the client would drop it if it came — pinned by a test with a leaked-detail reply); silence until the deadline → `.generic(error.tunnel_op_failed)`, not `.commandTimeout` (that text is about `wg show`).
    - `ServiceState.swift` — `helperSocketPath` and `ServiceState` (`absent`/`broken`/`outdated`/`installed`), derived from facts each tick by `ServiceState.derive(socketFileExists:outcome:)`.
    - `InstallerService.swift` — daemon install/uninstall via osascript `do shell script ... with administrator privileges`; static pure functions (script resolve, bundled-binary preflight, argv build, exit-code interpretation) are the tested part; the prompted run is not automatable.
    - `Model.swift` — `WGInterface { name, displayName, peers }`, `WGPeer { publicKey, endpoint, allowedIps, latestHandshake: Date?, rxBytes, txBytes: UInt64 }`, `TunnelInfo { name, isUp }` (a wg-quick config from the daemon's `state`; `isUp` is daemon data, refreshed by every `state` reply — menu open, up/down reply, serviceState transition — never derived from the snapshot), `TunnelState { name, isUp, utun }` (one `state` line; `utun` is set only for an up tunnel).
    - `DumpParser.swift` — global `parseWGShowDump(String) -> [WGInterface]` (tab-separated; interface line = 5 fields, peer line = 9; epoch `0` = never; `(none)` → nil).
    - `HandshakeFreshness.swift` — freshness enum with thresholds (fresh ≤ 120 s, aging ≤ 600 s) and `RouteScope` (fullTunnel/splitTunnel/none from allowed ips).
    - `Formatters.swift` — `formatBytes` (binary KiB/MiB/GiB) and `formatAgo` ("N ago").
    - `WireGuardRuntimeReader.swift` — stateless scanner of `/var/run/wireguard` → validated `config → utun` pairs (`WireGuardRuntimePair`), the single home of the freshness rule the namer used to carry inline: a `.name` entry needs an adjacent `<utun>.sock` with mtimes within 2 s (mirroring `get_real_interface` from wg-quick's darwin.bash — the sock is per-interface, so a recreated sock exposes a lingering stale `.name` on a reused utun); broken or unreadable entries are dropped, a missing directory yields an empty result; injectable file system (reuses `WireGuardTunnelNameFileSystem`) and `directoryPath`; no cache — every `readPairs()` rescans (the daemon's `state` depends on that), `isPairCurrent(configName:interfaceName:)` validates a single pair without listing the directory (the namer's cache-validation path). Used by the namer (which adds the cache) and by the daemon (`state`).
    - `WireGuardTunnelNamer.swift` — resolves `utun2` → wg-quick config name (`work-vpn`): a caching layer over `WireGuardRuntimeReader` — lock-protected cache with per-lookup re-validation via `isPairCurrent` (a reused utun must not show a stale config name), lazy rescan only for an unknown utun, `rescan()` for ⌘R. In daemon mode the root-owned `.name` files (0400 root) are unreadable for the app, so the namer misses every lookup there — the daemon's `state` mapping wins (see data flow) and the namer remains the source for the sudo dev fallback and interfaces the reply doesn't cover.
    - `StatusCardView.swift` — `StatusCardViewModel` (pure, tested) + thin SwiftUI `StatusCardView`.
    - `TunnelRowView.swift` — `TunnelRowViewModel` (pure, tested: `isBusy` = this tunnel's operation in flight, `isEnabled` = no operation in flight at all) + SwiftUI `TunnelRowView` (●/○ dot, `ProgressView` spinner when busy, hit-testing off and dimmed while disabled, VoiceOver label `tunnel.accessibility.on/off`; observes the model so spinner/clickability/isUp update live without a menu rebuild).
    - `StatusItemController.swift` — owns `NSStatusItem` and `NSMenu`; menu structure as data (`StatusMenuStructure`/`StatusMenuFactory`, tested; tunnel rows reach the factory via a `tunnelItemProvider` closure, same pattern as `cardItemProvider`) + `CardMenuItem`/`TunnelMenuItem` (native highlight disabled; clicks inside don't close the menu) + `StatusIcon` (menu-bar PDF icons, template) + legend visibility (`isLegendVisible` lives here so it survives `menuNeedsUpdate` rebuilds — the card's `@State` resets with each new `NSHostingView`; seeded into the card via `initialLegendVisible`, the ⓘ toggle reports back via `onLegendChange`, and the card re-measure is dispatched to the next run-loop pass — a synchronous `fittingSize` read would see the pre-render height and the ⓘ row would stay clipped until the next tick). `menuNeedsUpdate` also calls `model.loadTunnels()`; a separate `$tunnels` subscription rebuilds the section while the menu is open (the `state` reply is async — without it the section would appear only on the second open; a closed menu just rebuilds fresh next time). `modelDidChange` tracks `serviceState` transitions and, while the menu is open, reloads tunnels and rebuilds the menu on a change (a dead daemon removes the clickable rows — a click would be a guaranteed `connectionRefused`; a daemon that came up pulls the tunnel state without waiting for a reopen; a closed menu just rebuilds fresh next time).

Data flow: `WireGuardStatusModel.refresh()` picks the runner from facts on each tick — socket file exists (injectable `socketExists` probe) → `SocketWGShowRunner` over `/var/run/wgstatusbar.sock` (connect, send `show`, read to EOF under a 5 s deadline); no socket → the injected `commandRunner` (production: `ProcessWGShowRunner` = `/bin/zsh -lc "wg show all dump"`, login shell so Homebrew's `wg` is found on PATH; dev/sudo fallback). The dump arrives already sanitized from the daemon; it is parsed via `parseWGShowDump`, `displayName`s resolved through the namer (lazy rescan only for an unknown utun; `forceNameRescan: true` from the ⌘R menu item), then the daemon's `state` mapping (`stateInterfaceNames: utun → config name`, refreshed by every `state` reply) is applied on top — the daemon outranks the namer (the root-owned `.name` files are unreadable for the app, so in daemon mode the namer misses every lookup; without the override the 5-s tick would revert the card to `utunN`), and the namer stays the fallback for the sudo dev mode and interfaces the reply doesn't cover; a successful daemonless (fallback-runner) tick clears the mapping — once the daemon is gone, its last reply must not keep overriding the live namer resolve (utun reuse by another config would show a stale name); then `@Published` state updated on the main actor. A `Timer` re-fires refresh every 5 seconds. `lastFailure: StatusFailure?` lives one refresh cycle (`lastError: String?` is computed from it for the card); `serviceState` is recomputed each tick. Data from the last successful tick stays visible under a 10 s grace (`stalenessLimit`; a failed tick sets only `lastFailure`, never clears `interfaces`); past the limit the snapshot is stale (`isDataStale`, computed from `lastSuccessAt` set by the last successful tick) — the card dims it (opacity 0.5 + `status.stale_data` marker) and it no longer feeds the icon (`showsConnected`).

The menu is rebuilt in `menuNeedsUpdate` (always fresh on open): first item is the SwiftUI card in an `NSHostingView` (`CardMenuItem`, highlight off), then native items Refresh ⌘R / Open Configs ⌘O, then the Tunnels section, then the service item (from `model.serviceState`: `absent` → Install, `broken`/`outdated` → Update, `installed` → Remove) / Quit ⌘Q. The Tunnels section (separator + disabled header + one row per tunnel) sits between Open Configs and the service item and exists only when `serviceState == .installed && !tunnels.isEmpty` — an old daemon is reported `outdated` by the 5-s show tick (every reply carries versions; `state` is never sent to a non-installed daemon — on a pre-`state` build it is an unknown command) → Update item, no section. Rows are SwiftUI `TunnelRowView`s in `NSHostingView`s (`TunnelMenuItem`); a click calls `model.toggleTunnel(named:)`. One operation at a time: while `inFlightTunnels` is non-empty every row is non-clickable and dimmed, and Refresh ⌘R plus the service item (Install/Update/Remove) are disabled too — the install/uninstall scripts start with `launchctl bootout`, and a SIGTERM to the daemon mid-op would leave a half-applied tunnel; `performStatusAction` enforces the same no-op guard for service actions (the disabled re-render is asynchronous). A Refresh click would be a silently suppressed no-op — the tick is paused.

Tunnels data flow: `loadTunnels()` runs only when `serviceState == .installed` (an old daemon must not be poked — for a pre-`state` build it is an unknown command) on three triggers — menu open (`menuNeedsUpdate`), after an up/down reply, and on a `serviceState` transition while the menu is open (`StatusItemController.modelDidChange`; install-success needs no direct call — its `refresh()` flips the state asynchronously, and an identical `tunnels` array republishes nothing) — never in the 5-second tick (row states are daemon data; a tick never flips them — the interface snapshot is not consulted). Client errors are swallowed silently (menu data is opportunistic, it must not fake a card error in the sudo dev fallback; rows and names keep the last known). `tunnels` is built straight from the `state` reply — `isUp` is daemon data, never derived: `/var/run/wireguard` is root-only and the app cannot compute it (the original bug derived isUp from a displayName match, the daemon-side `.name` files were unreadable to the namer, every row read "down" and an up-click sent `up` into wg-quick's "already exists"). The same reply refreshes `stateInterfaceNames` (`utun → config name`) and applies it on both displayName write paths — in `loadTunnels()` (renames the card live while the menu is open) and in `refresh()` after the namer resolve (see data flow above). `toggleTunnel(named:)` inserts the name into `inFlightTunnels` → sends up/down (direction from the `tunnels` lookup — a row without a state answer honestly reads "down") → removes the name; a call while `inFlightTunnels` is non-empty is a silent no-op (the model, not just the disabled rows, enforces one op at a time — the 13 s queue budget holds exactly one op, and SwiftUI's disabled-rows re-render is asynchronous anyway); success → optimistic `isUp` flip (the daemon `ok` already proves the new state; the `state` reply arrives later, queued behind the refresh `show`, and converges — without the flip a repeat click in that window would resend the same command into wg-quick's "already exists" error; a delayed pre-op `state` reply cannot cancel the flip — `loadTunnels()` applies replies latest-wins via `loadTunnelsGeneration` (mirroring `refreshGeneration`): the sequential daemon orders reply sends, not client-side applications — each exchange runs through its own GCD thread → continuation → MainActor hop — and every op completion bumps the generation in the same MainActor block that sets the flip, so a stale reply is either applied before the flip or discarded) + immediate `refresh()` + `loadTunnels()`; failure → one-tick `lastFailure` + `loadTunnels()` **without** `refresh()` (the refresh prologue erases `lastFailure` synchronously — the error would never render; the next 5-s tick converges the data). While `inFlightTunnels` is non-empty `refresh()` returns immediately (no error, no `serviceState` change — the queued-show-silence would read as `broken`) and `isDataStale` is forced false (the 13 s worst-case queue outlives the 10 s `stalenessLimit`; without this the icon would dim mid-operation).

Security constraint: the raw dump contains secrets (private key, preshared key) — never log it anywhere. The daemon strips secret fields via `sanitizeWGDump` before anything leaves it, so secrets never enter the app process; the parser additionally skips them.

Privileged daemon details:

- Wire protocol (line-based, one connection = one request): `→ show | list | state | up <name> | down <name>`; `← ok <protocol> <build>\n<dump-or-names-or-state-lines-or-empty>`; `← err <protocol> <build> <code>[ <detail>]` with codes `wg-missing` | `wg-failed` | `wg-quick-missing` | `tunnel-not-found`. Both version numbers appear in every reply, including `err` — outdated detection works on error answers too (any `err` still carries versions, e.g. an unknown command answered `err wg-failed`; in practice the app learns "outdated" from the show tick's header, since tunnel requests are guarded on `.installed`). `state` (build 17+) is the current app's single source for row states and interface names; the wire `list` stays served for older apps — the current client no longer sends it. Tunnel-op `err` replies carry **code only, no detail**: wg-quick's stderr echoes executed commands (including Pre/PostUp hooks from the config) and child-wg errors can quote config lines, so the stderr tail is written to the daemon's stderr (→ `/var/log/wgstatusbar-helper.log` via the plist; 0600 root:wheel, pre-created by the install script — launchd would create a missing log world-readable 0644) and never crosses the wire.
- Budget invariants (pinned by tests, numbers from the constants): `show` — `WGShowExecutor` 3.0 + 2 × 0.5 = 4.0 s under the show client's 5.0 s deadline; tunnel ops — `WGQuickExecutor` 8.0 + 2 × 0.5 = 9.0 s (the marker path answers in ~2–4 s; the 9 s budget bounds the marker-with-delay, the kill escalation and the pipe-EOF wait alike); worst-case sequential queue (a `show` started before the op) 4.0 + 9.0 = 13.0 s < `SocketTunnelClient.opTimeout` 16.0 s, so the daemon always answers before the client gives up.
- wg-quick PATH invariant: the executor replaces the child's whole environment with `PATH = /opt/homebrew/bin:/usr/local/bin:/opt/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` (resolver dirs first, system tail, deduped; pinned by a test). Under launchd the daemon has no Homebrew PATH — `wg-quick` is `#!/usr/bin/env bash` requiring bash ≥ 4 (system 3.2 dies with "Version mismatch") and calls `wg`/`route`/`ifconfig`/`networksetup` from PATH; verified empirically on the dev machine (launchd PATH → fails, brew-first PATH → works).
- Version constants live in `HelperProtocol.swift` (Core): `helperProtocolVersion` is compared for equality (bump only on breaking format changes); `helperBuildNumber` is monotonic — **bump it whenever helper code changes (release checklist)**; an app carrying a newer build reports the daemon `outdated` and shows the Update menu item.
- Service state is derived, never stored: no socket file → `absent`; socket present but connect refused / silence until the client deadline / garbage / instant EOF → `broken`; wrong protocol or older build → `outdated`; healthy → `installed`. `wgMissing`/`generic` errors don't affect service state (the daemon is fine, wg is the problem).
- Paths: socket `/var/run/wgstatusbar.sock` (0660 root:admin; the server unlinks a stale file before binding); helper binary `/Library/PrivilegedHelperTools/com.stuchalin.wgstatusbar.helper` (755 root:wheel); plist `/Library/LaunchDaemons/com.stuchalin.wgstatusbar.helper.plist` (`RunAtLoad` + `KeepAlive`, stderr → `/var/log/wgstatusbar-helper.log`, 0600 root:wheel — pre-created by `install-daemon.sh` because launchd creates a missing log world-readable, and the wg-quick stderr tail can quote config lines).
- Install scripts: `scripts/install-daemon.sh --binary <path>` (idempotent: bootout ignoring "not loaded" → copy to a temp name + atomic rename over the live binary, so an async-bootout old daemon is not truncated under a running process → rm the socket file before bootstrap — the old daemon never rebinds, so only the new daemon's bind can recreate it and the wait below is a real "new daemon is up" signal on updates too, not just fresh installs → bootstrap system with a short retry → bounded wait until the daemon answers — a `show` request over `nc -U` gated on an `ok`/`err` reply header, not just socket-file existence: `bind()` creates the file before `listen()`, so a file-only check can pass in the bind→listen window and the app's immediate post-install refresh would hit a refused connect and mark the fresh service broken for a tick — so the refresh doesn't race into the fallback runner, a stale socket, the old daemon, or that refused connect → pre-create the daemon log root-only — `touch` + `chown root:wheel` + `chmod 600` before bootstrap: launchd creates a missing log world-readable 0644, and the daemon's stderr tail can quote config lines; launchd appends to the existing file and keeps its mode, so re-installs also fix older 0644 logs) and `scripts/uninstall-daemon.sh` (bootout → rm plist, binary, socket, log); both ship in the .app's `Contents/Resources/` (`build-app.sh` also copies the helper binary to `Contents/MacOS/`).
- Install flow from the menu: `StatusItemController.performStatusAction` → `ServiceInstalling` (InstallerService) → osascript with the system password/Touch ID prompt. Cancelled prompt is a silent no-op; success triggers an immediate `refresh()`; script failure puts its stderr into the one-tick error.
- Accepted risk (documented in README): the install path runs a root shell script from the user-writable app bundle with no checksum (TOCTOU); the daemon likewise executes `wg` — and now `wg-quick` — from user-writable Homebrew paths as root (same local-user→root family). `wg-quick` additionally executes each config's Pre/PostUp (Pre/PostDown) hooks as root, and the configs live in user-writable directories — editing a config is arbitrary-code-as-root on toggle. There is deliberately no mutual exclusion between tunnels (wg-quick keeps several interfaces; two full-tunnels raised together fight over the default route and system DNS — README warns). The real fix is Developer ID + SMAppService plus a root-owned copy of `wg`/`wg-quick` (and configs) at install time, a future migration the protocol is designed for (transport change only).

Domain rules:

- Peer `isActive` = handshake freshness is `fresh` or `aging` (green ≤ 2 min, orange ≤ 10 min, inclusive).
- Interface `isConnected` = any of its peers is active.
- Menu-bar icon flips between `StatusIconOn`/`StatusIconOff` (vector PDFs in `Resources/`, loaded via `Bundle.module`, `isTemplate` so AppKit recolors for light/dark; error state shows Off). The icon and `menu.title.on/off` (the VoiceOver accessibility label) read `showsConnected` = `isAnyConnected && !isDataStale` — a snapshot older than `stalenessLimit` never lights the icon, so losing the source dims the shield within ~10–15 s (grace + one 5 s tick) instead of freezing it "on"; a single failed tick inside the grace causes no flicker. `isAnyConnected` stays the plain data-level truth.

## Localization

All UI strings go through `L10n.string(key, args...)` (loads from `.module` bundle). Every new key must be added to **both** `Sources/WGStatusBarCore/Resources/en.lproj/Localizable.strings` and `ru.lproj/Localizable.strings`; format placeholders use `%@` only (numbers passed as strings).

## Testing notes

- Tests use `@testable import WGStatusBarCore`. Injection points on the model: `WireGuardStatusModel(testing:)` injects interfaces directly (no timer/network), `init(commandRunner:tunnelNamer:)` injects protocol mocks for refresh-flow tests, `init(commandRunner:tunnelNamer:socketExists:socketPath:)` additionally injects the socket probe for service-state tests; the same full init takes `now: () -> Date` for staleness-grace tests (a frozen `FakeClock`) and `tunnelCommandRunner: TunnelCommandRunning` for tunnel tests (mock with counters and programmable results). Non-empty interfaces injected via `init(testing:)` always read as stale (`lastSuccessAt == nil`), so "on" assertions on `showsConnected`/`menuTitle` must go through a successful refresh (`makeRefreshedModel` in `WGStatusBarTests`).
- Parser tests call the global `parseWGShowDump(_:)` with fixture strings — no process spawning there. Tests spawning processes are `ProcessWGShowRunnerTests`, `WGShowExecutorTests` and `WGQuickExecutorTests`: short-lived executable stubs with injected small timeouts. `WGQuickExecutorTests` stubs are zsh scripts resolved through an injected single-candidate `searchPaths` (arguments are literal `["up"|"down", name]` and are asserted via marker files, not injected); the PATH test has a stub print `$PATH` and asserts the brew directories precede the system ones; timeout tests use ≥1.5 s deadlines — with a replaced environment (PATH only) a zsh script needs ~0.5 s to reach its first line, so a 0.3 s TERM would kill the stub before it sleeps. The launchd-`wait` behavior of `up` is stubbed: a script that prints `upMonitorMarker` to stderr and sleeps must return ok fast (marker path, script SIGKILLed, the kill-ok probe-confirmed — its dead-probe twin must fail honestly with a `killed by signal` detail), a script that prints the marker and then exits nonzero must fail honestly with the failure text from stderr in the detail (marker ≠ success — PostUp failure under `set -e`; the snapshot carries the tail even when a background pipe-holder keeps EOF from ever arriving), a script whose "hook" outlives the kill delay is SIGKILLed mid-flight and returns ok with a live probe (the pinned far side of the grace window — a late hook failure is unobservable by design), a stub whose hook-echo `[#] …` line or foreign output line merely contains the marker substring must NOT trigger the marker path and falls to an honest `timedOut` (whole-line marker matching — a PreUp echo must not fake setup completion), a hanging script with an injected `tunnelUpProbe = true` must return ok on the timeout path, a stub that exits leaving a background pipe-holder (`sleep 5 &`) must return within the budget (bounded pipe-EOF wait — regression for the accept-loop wedge), a non-executable resolved binary must fail as launch-failure `.failed` without hanging, a hanging `down` stub (even printing the marker, even with a live probe) must stay `timedOut` (down runs without marker and without probe — anti-copy-paste invariant), and `tunnelIsUp` is unit-tested against a fake FS carrying per-file type+mtime, including the strict mtime boundary (Δ = 2 s rejected, 1.99 s accepted).
- Daemon socket logic is tested in one process: `HelperDaemonTests` runs a real `DaemonServer` on a tmp socket with a stub executor (plus a stub config store / stub tunnel executor / stub runtime-reader FS for the `show`/`list`/`state`/`up`/`down` routing — state cases: mixed up/down lines with the store's ordering, empty runtime directory → all down, a pair removed from the fake FS between two consecutive requests → the second answer is down (fresh scan per request) — plus invalid-name, error-mapping and EOF-during-op cases); `SocketWGShowRunnerTests` and `SocketTunnelClientTests` drive the clients against it — no root, no real `wg` (a DaemonServer needs the stub dump to end with `\n`, like real `wg` output, or the client rejects it as truncated). `SocketTunnelClientTests` also drives the `state` round-trip against the live server (up with utun / down without, empty config set → `[]`, garbage payload lines → `badResponse`, old daemon build → `daemonOutdated`), pins the budget invariant (constants only) and runs one full-stack test: a real `WGQuickExecutor` with a marker-printing zsh stub behind the live `DaemonServer`, `up` via `SocketTunnelClient` → fast `ok` (routing + classification seam).
- `InstallerServiceTests` cover the pure static functions only (script resolve, osascript argv, exit-code interpretation) — the privileged prompt is not automatable.
- `WireGuardRuntimeReaderTests` and namer tests inject a fake file system (`WireGuardTunnelNameFileSystem`); reader cases: valid pair, `.name` without a neighboring `.sock`, `.sock` without `.name`, mtime divergence on a recreated sock (lingering `.name` on a reused utun), the strict mtime boundary (Δ = 2 s rejected, just under accepted), empty/whitespace/unreadable `.name` contents, missing directory, re-scan on every call, plus the `isPairCurrent` single-pair checks. `TunnelConfigStoreTests` inject a fake FS the same way (`TunnelConfigFileSystem`); `WGQuickResolverTests` mirror `WGBinaryResolverTests` with an injected `fileExists`. Card, menu and tunnel-row logic are tested through `StatusCardViewModel`, `StatusMenuStructure`, `TunnelRowViewModel`, `StatusItemController.performStatusAction`, `StatusItemController.iconConnected(for:)` and `StatusItemController.shouldReloadTunnelsAndRebuildMenu(previous:current:isMenuOpen:)` (no `NSStatusItem`/`NSHostingView` in tests).
